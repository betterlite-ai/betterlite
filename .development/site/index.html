Porting LiteLLM to Rust

betterlite rewrites LiteLLM in Rust under the MIT license. Coding agents build it one task at a time, and a task merges once its gate passes. This page reads the task list on main and is rebuilt after every merge.

Two stages

Counts per day go by merge time. Times and sizes per pull request go by when the work started: stage 2 holds the pull requests whose first commit came after the switch, and one that started before and merged after counts only in All.

Stage 1, until #722 merged. A worker agent wrote the task and ran its whole check list on the laptop before the pull request opened: the build, the task's tests, the oracle cases that compare answers with LiteLLM, and the mutation tests. Every task checkout kept its own build folder, several gigabytes each. With dozens of agents at once the builds filled the disk, wrote to it all day and slowed every agent down. CI then checked lint on the pull request and ran the task's tests again in the merge queue.

Stage 2, from #722 on. On the laptop a worker only formats and lints the code and runs the checks that need no test build. The tests, the oracle cases and the mutation tests run in CI on the pull request. A red run goes back to the same worker with the failing lines, the reviewer checks the fix, and after three red rounds the task is marked blocked. The merge queue still tests the merged result before it reaches main.

What should change: less disk traffic and less waiting on the laptop, so pull requests open sooner. What it costs: more CI runs, and some tasks need an extra round when CI finds what the laptop no longer checks. The table below shows both sides.
